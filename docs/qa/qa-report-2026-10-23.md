## Concurrency

All 10 cases held in every one of their 20 runs: no 5xx responses, and capacity never exceeded. The pool has 10 connections, and 5–10 were in use at once during each run, so the requests really overlapped.

After every run, four invariants were checked: booked count equals confirmed bookings, booked count stays within capacity, every promoted waitlist entry points at a confirmed booking, and nobody is both booked and waiting for the same class.

| Case | Setup | Result over 20 runs |
| --- | --- | --- |
| Final seat | 10 members, capacity 5, 4 already booked | 1× 201 + 9× SESSION_FULL; final count 5/5 every run |
| Empty class | 10 members, capacity 3 | 3× 201 + 7× SESSION_FULL every run |
| Same member | 5 requests at once | 1× 201 + 4× ALREADY_BOOKED; exactly 1 booking row |
| Cancel vs 9 bookers | full class, 1 waiting | waiting member always promoted; all 9 bookers got SESSION_FULL |
| Cancel vs 9 waitlist joins | timings rotated | joins first in 3 runs, cancel first in 17; never a free place while someone waits |
| Double cancel | 2 owner + 3 admin requests, 1 waiting | 1× 200 + 4× BOOKING_ALREADY_CANCELLED; exactly 1 promotion and 1 "you got a place" email |
| Waitlist order | 4 waiting, 3 cancels + 3 bookers | first 3 in line promoted once each; 4th still waiting |
| Capacity 5→4 vs 6 bookers | timings rotated | edit 200 in 13 runs, CAPACITY_BELOW_BOOKINGS in 7; count never above capacity |
| Capacity 3→6 vs 7 bookers | 2 waiting | both waiting members promoted every run; at most 1 direct booking, only after them |
| Delete vs 5 bookers | never-booked class | delete won 13 runs (bookers got 404); bookings won 7 (delete got SESSION_HAS_BOOKINGS); no orphan rows |

In the "cancel vs joins" case, no single run mixed both orders; the window between them is under a millisecond.

## Defects

Three defects were found: one in the product and two in the e2e test setup. None affects booking safety.

| # | Defect | Severity | Owner |
| --- | --- | --- | --- |
| 1 | Admin search doesn't find a class by member name | Medium | frontend-admin, plus the lead |
| 2 | Email links in e2e runs point at the wrong server | Low–medium | backend-member (D4 config) |
| 3 | `yarn test:e2e` doesn't work as configured during development | Low | backend-member, plus the lead |

**1. Admin search by member name.**

1. Create a class and book it as a member named "Quinnella X".
2. Open `/admin` and type "Quinnella X" in the search box.
3. Expected (§4.2, qa.md C): the class appears.
4. Actual: "No classes match … Member names are searched in rosters you've opened."

Search only knows member names for rows already expanded, because the schedule list response carries no member data. A fix needs either a contract change or fetching the rosters.

**2. Email links in e2e runs.** `playwright.config.ts` sets `APP_URL` on the Next server, but the API builds the emails. In e2e runs, links point at `localhost:3000` instead of `:3100`. They only opened here because a dev server happened to be running on 3000; in CI they'd be dead links.

**3. e2e config during development.** Next 16 allows one `next dev` per project folder, so Playwright's server fails to start while a dev server runs on 3000. Separately, `reuseExistingServer` skips `yarn seed` when the API is already up, so tests can run on stale data.

**Not run as specified**

- Lighthouse: not installed; the lab LCP/CLS measurement above was used instead.
- `yarn test:e2e` exactly as configured: blocked by a running `next dev` (defect 3). The production build was served on port 3100, which Playwright reuses, and the database was seeded by hand first.
- Stopping the real Mailpit: not done. The outage was simulated with an API pointed at a closed mail port.

**Environment notes**

- Another process truncated the shared `studio_spot_test` database mid-run. QA runs used a new isolated database, `studio_spot_qa_test`, which is kept for reproductions.
- `.env` changed during the session: `ADMIN_PASSWORD` is now 10 characters, which makes `yarn seed` fail (12-character minimum). Seeding used the `.env.example` password set explicitly.
- The dev database `studio_spot` now holds QA test classes and a second admin, `qa-admin-two@studio.local`. Re-seed to reset it.
